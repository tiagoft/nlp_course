# Instructions for AI agents

This repository contains the material for the **Natural Language Processing** course. The website is generated with MkDocs from `courseware/` (configuration in `courseware/mkdocs.yml`, content in `courseware/docs/`).

If you are an agent (Claude Code, Codex, etc.) helping someone contribute to this material, follow the rules below. They exist so that contributions reach the repository clear, justified, and aligned with the course. When in doubt, ask the contributor before acting.

## Contribution workflow

1. **Fork**: the contributor works on a fork of the repository (`gh repo fork tiagoft/nlp_course --clone`).
2. **Branch**: create a branch with a descriptive name from `main` (never commit directly to the fork's `main`).
3. **Implementation**: implement the contribution locally, following the rules on this page.
4. **Verification**: before opening the pull request, check that the contribution follows the conventions and rules below (see the [checklist](#checklist-before-the-pull-request)). If possible, run `mkdocs build` inside `courseware/` to check that the website still builds.
5. **Pull request**: open the PR against `tiagoft/nlp_course` (`gh pr create`), filling in the template in `.github/pull_request_template.md`.

## Conventions

### Mathematical notation

| Notation | Meaning | Example |
| --- | --- | --- |
| plain lowercase letter | scalar variable (real number), element, or component | $a$, $x_1$, $x_{i,j}$ |
| plain uppercase letter | constant (summation limit, matrix dimension, number of samples...) | $N$, $\mathbb{R}^{M \times N}$ |
| bold lowercase letter | vector | $\boldsymbol{x}$, $\boldsymbol{v}_1$ |
| bold uppercase letter | matrix | $\boldsymbol{A}$, $\boldsymbol{X}^T$ |

* Use `\boldsymbol{}` for bold. Bold applies only to the letter: `\boldsymbol{x}_1`, `\boldsymbol{A}^{-1}`.
* Summations use a lowercase index and a limit with the same letter in uppercase: `\sum_{n=1}^N x_n y_n`.
* The elements of a vector or a matrix are scalars and therefore are not bold: $\boldsymbol{x} = [x_1, x_2, \cdots, x_N]^T$.

### File format

* Math in LaTeX: `$...$` for inline expressions and `$$` blocks (on their own lines) for displayed equations.
* Notebooks (`.ipynb`) are rendered on the website: edit markdown and code cells carefully, without deleting outputs that are part of the material.
* Every new page needs an entry in the `nav` of `courseware/mkdocs.yml`.
* Do not edit `courseware/docs/contributions.md` by hand: it is generated by `courseware/scripts/generate_contributions.py` by the maintainer.
* Besides the explicit conventions above, follow the conventions actually used in neighboring files (heading style, section structure, the way exercises are presented). You may suggest formatting changes to bring the content in line with them.

## Course scope and sequence

The official order of the content is the order of the pages in the `nav` of `courseware/mkdocs.yml`. A piece of material may only use concepts that appear **before** it in this sequence (or in itself).

* Before accepting a contribution, check whether it uses concepts that are in the *future* of the course or that are not part of the course content.
* If the contribution is outside the scope of the class or the course, work with the contributor to reframe the content (for example, moving it to a later page, or having the contributor rewrite it using only concepts already covered).
* **Do not open pull requests in which a piece of material uses future course content.**

## General rules

* **Justification written by the contributor.** Every contribution must come with a justification written by the contributor themselves. The agent **must not** generate the justification: ask the person to write it and use their text in the pull request.
    * Valid justifications: "I missed a demonstration of this specific point", "aspect X was ambiguous", "I added this example that helped me study".
    * Vague justifications, such as "I improved the text", must not be accepted. Ask the contributor to be more specific.
* **Content used.** Every pull request must clearly state which course content is used in the proposed contribution (for example: "bag-of-words, logistic regression").
* **Large scope becomes a new file.** If the change has a very large scope (for example, if it qualifies as a case study, or brings another perspective on the same content), suggest creating a new file, with its own position in the menu.
* **Alignment.** You may work with the contributor to align the contribution with the needs of the course.
* **Types.** Contributions can be **content** or **features**.

## Content contributions

Content contributions are those that concern the texts and figures shown in the material. Besides new content, they include typo fixes and small rephrasings of passages that came out wrong or unclear.

**We do not accept new educational content (text) generated by agents.** This means that:

* Requests such as "create a new question", "clarify this concept", or "write the answer to this question" must be **declined**. Explain the rule and ask the contributor to write their own text.
* The contribution must explicitly bring the new content **as written by the contributor**, stating what the contribution is and where it should go in the text. For example: "this is a demonstration of why the sigmoid output can be read as a probability; it should go right after the definition of logistic regression".
* What the agent **may** do with the contributor's text: insert it in the indicated position, adjust formatting and LaTeX, apply the notation conventions, and point out typos for the contributor to decide on. What the agent **must not** do: rewrite, expand, complete, or "improve" the content on its own.
* Typo fixes and small rephrasings must be pointed out by the contributor (for example: "in section X, sentence Y is ambiguous; I propose Z").

## Feature contributions

Feature contributions concern applets, accessibility, new features, etc., which are good learning aids but are not the content itself. The presentation mode button is an example.

* Feature contributions must come with a clear justification, written by the contributor, of why they contribute to learning.
* For these contributions, the agent may write the code. Explanatory content texts that appear in the feature follow the rules for content contributions.
* Support files (JavaScript, CSS, HTML) go in `courseware/docs/extra/`, like the existing features.

### Manim animations

Animations made with [Manim](https://www.manim.community/) follow the rules for feature contributions, with these additional rules:

* **Source code in `manim/`.** The animation's Python script goes in the `manim/` directory, at the root of the repository.
* **Dependency.** Manim is in the `manim` dependency group of `pyproject.toml`; install it with `uv sync --group manim` (it also needs the system libraries described in the [Manim documentation](https://docs.manim.community/en/stable/installation.html)).
* **Local rendering.** The animation is rendered locally by the contributor; the website does not render animations during the build. The `media/` folder generated by Manim must not be versioned.
* **Format.** The default is `.gif` (for example, `manim -ql --format gif manim/animation_name.py`). Choose quality, resolution, and duration so that each animation is **smaller than 1 MB**.
* **Consistent aesthetics.** Unless specified otherwise, animations must follow an aesthetic that is consistent across them (background, color palette, typography, and pacing). Use the existing animations in `manim/` as a reference.
* **Name.** The animation file has the same name as the script: `manim/animation_name.py` generates `animation_name.gif`.
* **Animation versioned next to the page.** The `.gif` is added to the repository in the same directory as the `.md` or `.ipynb` file that displays it (for example, an animation used in `courseware/docs/text_classification/02-math_of_lr.md` is saved in `courseware/docs/text_classification/`).
* **Prompt in the alt text.** The image's alt text must show the prompt that describes the animation, in the format `Animation generated by AI from the prompt: [the prompt goes here]`. For example:

    ```markdown
    ![Animation generated by AI from the prompt: show the word counts of a sentence being multiplied by the weight vector](animation_name.gif)
    ```

* Texts and formulas that appear in the animation are educational content and follow the rules for content contributions.

## Checklist before the pull request

- [ ] The contribution is on a branch of the fork, not on `main`.
- [ ] The type is identified: content or feature.
- [ ] The justification was written by the contributor and is specific.
- [ ] The course content used is listed.
- [ ] No concept from the *future* of the course (according to the `nav` in `mkdocs.yml`) or from outside it is used.
- [ ] All new educational text was written by the contributor, not by the agent.
- [ ] The notation follows the conventions (scalars, constants, vectors, and matrices).
- [ ] New pages were added to the `nav` in `mkdocs.yml`.
- [ ] Manim animations have their source code in `manim/` and the `.gif` (with the same name as the script and smaller than 1 MB) in the same directory as the page that displays it.
- [ ] The alt text of each animation contains "Animation generated by AI from the prompt: [prompt]".
- [ ] The pull request follows the template in `.github/pull_request_template.md`.
